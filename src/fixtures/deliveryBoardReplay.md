# Synthetic delivery board replay

These are fictional response projections, not a captured live board or a claim about an eligible live null-review merge. The two repositories have fifty open Issues, twenty open PRs, one shared 580-row Project, and ten prepared host-local queue entries. Native list/read APIs and existing strict Project/queue owners remain active; only external client/context ports and forbidden writers are replaced.

The eligible PR projection explicitly uses observed null review, non-draft MERGEABLE/CLEAN facts, a current base and a pinned successful App check. It supplements the recorded zero-approval regression in `recordedGitHubFlows.ts`. Journal comments use created time and full numeric IDs, including an adjacent pair beyond JavaScript safe-integer precision.

The native context uses `ai-delivery.github@1` and the loader digest over `{ sourceDigest, routing, roles }`; client/context ports enforce the selected author and role settings.

Every request records operation counts. A successful two-repo inventory requires six `ProjectDeliveryItems` pages and zero per-item status reads, for both one and fifty selected Issues. Queue bytes and checkout configuration are hashed before/after; target scripts, enqueue/advance and checkout setup are denied. Owned temporary roots are identity-checked, removed on test completion, and recorded in existing test output.

Faults exercise unreadable repositories, Project-only denial, repeated cursors, missing/unsupported/duplicate status, ambiguous/unreadable latest journals, independent metric windows, search ceilings, duplicate IDs, missing merge commits, retained-data bounds, late failure and incompatible queue state. No credentials, remote fixture, new runner or latency gate is used.
